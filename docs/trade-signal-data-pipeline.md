# trade-signal 数据管线（数据源与复权体系）

> `scripts/`（python）数据灌入管线的设计口径权威文档。命令用法见 [../scripts/README.md](../scripts/README.md)，本文档负责"为什么这么设计、口径是什么、有哪些坑"。表结构以 [trade-signal-schema.sql](trade-signal-schema.sql) 为准。

## 1. 定位与架构

薄脚本层，与 Java 主体**通过数据库解耦**：python 只写库，Java 只读库（Java 侧不落任何计算结果）。

```
akshare（三源）──► scripts/fetch（取数）──► scripts/adjust（因子反推复权）──► trade_signal 库 ──► Java 只读
```

写入的四张表：

| 表 | 内容 | 写入方式 |
|---|---|---|
| `stock_info` | 股票基础信息（name/market 唯一来源、board_type 板块枚举） | 全量灌入，akshare 名单接口 |
| `stock_quote` | 日线 OHLCV：`ADJUST='0'` 原始行 + `ADJUST='1'` 自算前复权行 | 原始行只追加；qfq 行可重算覆盖 |
| `stock_dividend` | 除权除息事件（EX_DATE + 综合因子 k + SOURCE） | 双轨生成：公告日历=权威日历，因子反推=测 k+校验+兜底，只追加 |
| `work_day` | 交易日历（`/kdj/periods` 来源） | 从 stock_quote distinct TRADE_DATE 生成 |

ID 规则：`stock_quote`=MD5(code:yyyymmdd:adjust)、`stock_dividend`=MD5(code:ex_date)、`work_day`=MD5(market:trade_date)；时间戳一律 UNIX 秒（DECIMAL(15,0)）。

## 2. 数据源实测口径（2026-08，本机实测）

| 源 | 状态 | 说明 |
|---|---|---|
| **新浪 `stock_zh_a_daily`（唯一行情源）** | 可用 | **等比前复权**，factor 阶梯干净（平台波动 ~1e-5）；沪深北通吃；成交量单位为股；**数据滞后一个交易日**（周六跑时本周五已齐）。缺点：无视日期参数、每次返回全历史（~15-20s/股），故增量只能**周频**（见 §3.2） |
| 东财 `stock_zh_a_hist` | **退出生产**（仅留应急兜底代码） | 服务器端限流实录：全量窗口抓取触发限流、连续 3 天不稳定（2026-08-05~07 日增试运行），"熔断器+盘中行过滤"方案作废；本机 push2his 直连亦被重置、代理 502 |
| **东财 `stock_history_dividend_detail`（公告日历）** | 可用 | datacenter-web 接口（与 push2his 不同域，不受行情限流影响），本机与服务器均通；分红（送/转/派每 10 股）+ 配股（方案/价格/除权日）两 indicator；坑：个别行公告日期是 1900-01-01（垃圾字段），只依赖除权日；同一除权日可兼有分红与配股，按日合并 |
| 腾讯 `stock_zh_a_hist_tx` | **弃用** | 其 qfq 是**等差（减法）复权**：段内 qfq=raw−C，factor 随价格漂移，不是阶梯，会产生大量伪事件（实测踩过并清理） |

其他口径：

- 每股必须爬**两口径**（`adjust=""` 与 `adjust="qfq"`）且**必须同源**（复权基期才一致）
- 北交所代码 2024 年起已整体迁移 920 段（如 贝特瑞 835185→920185），板块前缀规则 `92x→'3'` 已覆盖
- 取数纪律：`NO_PROXY=*` 强制直连（本机系统代理会致抓取失败）、串行真限流、指数退避重试 3 次、行情源只认新浪

## 3. 复权：因子反推法 + 公告日历双轨

每股爬两口径价格，`factor(t) = qfq(t) ÷ raw(t)` 是**阶梯函数，只在除权日跳变**，跳变倍数即综合因子（红利/送转/配股合并效果）。2026-08-04 起事件判定采用**双轨制**：**东财公告日历 = 权威事件日历；因子反推 = k 值测量 + 校验 + 兜底**。

- **双轨合并规则**（`adjust/merge.py`）：
  - 公告除权日 ±3 个交易日内有反推事件 → 用反推 k，`SOURCE='derive+announce'`（主口径）
  - 公告日无反推事件 → 理论公式算 k：`k = (P前收 − 派/10 + 配/10×配股价) ÷ (P前收 × (1 + (送+转)/10 + 配/10))`，`SOURCE='announce'`（早期低 qfq 价位段微额分红只能靠这条恢复，纯反推在噪声界以下物理不可分）
  - 反推事件不在公告日历 → **晋升落库，`SOURCE='derive'`**，suspect 清单仍输出仅作提示（2026-08-04 增补：东财分红日历对股改对价/缩股/重组是系统性缺口——000027 股改对价 20060426 实测坐实；修后五道闸实证零误报，丢弃真事件反而切碎平台段、污染自算 qfq）
  - 交叉校验：|k_理论/k_反推 − 1| > 0.5% → 人工复核清单（仍用反推 k 落库）
  - 东财公告不可用 → 回退纯反推五道闸，`SOURCE='derive'`
- **事件判定五道闸（全 AND，反推轨）**：
  ① factor 日际相对变化 >0.1%；② 隐含金额变化（×当日股价）>0.005 元（原始双阈值，静默过滤）；
  ③ **噪声自适应幅度下限**：|相对变化| > 1.5 × 0.01 元 ÷ **min(raw, qfq)**——factor 由两个各自 0.01 元舍入的价格相除得到，常数平台上逐日 factor 的舍入状态游走最大可达 ~1 个最小价位/较小价；**分母必须取 min(raw, qfq)**：等比前复权下早期 qfq 被累计因子压缩至分角级（万科 1991 年 qfq 仅 0.04~0.13 元），噪声由 qfq 侧主导，按 raw 价算的下限在早期形同虚设（000002 全量回填事故：1005 个伪事件，修复后 32 个存活候选）；对高价股此项趋近于零，无副作用；
  ④ **方向过滤**：等比前复权下除权日 factor 只会向 1 跳升（k = 前÷后 < 1），降向候选（k ≥ 1）物理上不可能是除权，直接丢弃；
  ⑤ **跳变持续性后验**：候选跳变点之后 5 个交易日的 factor 中位数须 ≥ 旧平台 + 0.5 ×（新平台 − 旧平台）——真除权后 factor 永久稳定在新平台，伪跳变（舍入振荡）数日内振荡回原平台
- **被弃候选留痕**：③④⑤ 丢弃的候选连同原因（amplitude / direction / persistence）保留在 FactorSeries.rejected，`scripts/verify_fix.py` 只读复跑可审计
- **事件因子 k**：跳变点前后各约 10 个交易日 factor 中位数相除。等比前复权下除权日 factor 向 1 跳**升**，故 k = 前 ÷ 后 < 1（每日增量"历史 qfq 行 ×= k"依赖此方向约定）
- **落库原则**：爬的 qfq 只作反推原料与对拍基准，**落库一律自算** `qfq = raw × factor`（平台段中位数）——任何时刻库里 qfq 可由 raw + factor 表重算，可审计
- 对拍校验：自算 qfq vs 爬取 qfq 全序列，**逐日自适应容差** = max(0.1%, 3 个最小价位 ÷ min(raw, qfq))——早期 qfq 低价段的"偏差"本质是爬取 qfq 自身的两位小数舍入抖动（自算值是段中位数去噪后的平滑序列，反而更接近真值），固定容差在该段无意义；近年段容差仍为 0.1%

### 3.1 历史回填流程（每股 4 次调用）

爬 none 全历史落库 → 爬 qfq 全历史（原料）→ 抓东财公告日历（分红+配股）→ 逐日 factor → 五道闸识别候选 → 双轨合并写 stock_dividend → 自算 qfq 落库 → 全序列对拍（自适应容差）。保险：合并后事件数 > 市龄×3 → 中止该股、不写事件/qfq 行、标记人工复核（full_backfill_review.txt）。

### 3.2 增量流程（生产口径：**周频**，2026-08-08 起每周六 09:17）

爬近 10 日窗口两口径 → 取库中尚无的交易日 → factor_当日 vs 库存最新 factor → 过与历史回填同款的闸①~④（相对/金额/幅度下限/方向）→ 无变化直接落库；候选事件再过闸⑤持续性后验（用 10 天回看窗口内该日之后的逐日 factor；后续不足 5 日则**延期判定**，当日行不落库、下次窗口前移后重评）→ 确认事件则 k=旧÷新 → stock_dividend 追加 → 该股历史 qfq 行 ×= k → 当日行落库。

**周频口径（用户拍板，"东财熔断器+盘中行过滤"方案作废）**：行情源统一新浪、**接受一周延迟**、每周六同步本周未爬数据。原因：新浪无视日期参数每次返回全历史（~15-20s/股），日频全量需 20+h 不可行；东财行情口曾支持小窗口（~3-6s/股）但服务器限流实录不可用。全量 `--all`（5535 只）周跑预计 **23~30h**（周六 09:17 起跑、周日傍晚前完），幂等 + flock 防重叠，漏跑下周自然补齐。增量结束后顺带刷 work_day（幂等 INSERT IGNORE）并预热扫描缓存（run_daily.sh 编排）。

### 3.3 调度

脚本是一次性 CLI（跑完即退），由 **OS 级调度**触发，不用 python 常驻进程定时（APScheduler 等）——无常驻看护、无内存泄漏累积、退出码可接告警。

生产实例（服务器）：
- **周频增量**：`/etc/cron.d/trade-signal-daily` → `17 9 * * 6 ops /home/ops/scripts/run_daily.sh`（**每周六 09:17**，17 分为反 herd 偏移；该文件必须 root:root 644，否则 cron 拒跑——trade-signal-backup 曾因此踩坑）。wrapper（700 权限）负责装配环境（`NO_PROXY=*`、`DB_PASSWORD` 从 `/etc/trade-signal.env` 经 sudo grep 提取——cron 非交互无 shell 环境）、flock 防重叠、日志按日期分隔追加到 `/home/ops/scripts/daily.log`，末尾依次刷 work_day、预热缓存（warm_cache.sh，周跑正好每周一次重算）。
- 本机 Windows 开发机：任务计划同理（仅作开发，生产在服务器）。
